# Roadmap

Not a backlog, not a promise. This documents features that were designed and deliberately **not** built, so the reasoning is preserved instead of re-litigated the next time someone asks "should clearfelt do X." If you're considering building one of these, read the "Why not now" section first, it's there to be argued with, not skipped.

Both entries below came out of the same design pass that produced `templates/constraints.example.md` and the personal-calibration work in `scripts/calibrate.mjs` (see `CHANGELOG.md`). That pass evaluated every proposed gap against one test: **can it be described without naming a platform, a person, or a project?** Anything that failed that test either got redesigned into a generic primitive (constraints, calibration) or landed here instead of shipping.

## Feature C: Structural-variety check against a corpus

**What it would do**: a generic `--avoid-repeating <dir>` flag on `/clearfelt audit` and `/clearfelt write`. For the most recent N files in the given directory, compute a lightweight structural fingerprint (opening-sentence shape, paragraph-count bucket, burstiness/MATTR proximity, all signals `scripts/lib/score.mjs` already computes, no new statistical machinery) and report similarity as a new, informational report section, alongside readability, not folded into the Human Score.

**Problem it would solve**: nothing today compares a new draft against a writer's own recent output. Every rule in `rules/antipatterns/` and `rules/banned_words/` scores one document in isolation. A writer who publishes serially (a blog, a newsletter, a weekly social post) and wants to avoid "this reads like my last three pieces" currently has no way to check that automatically; every downstream workflow that cares about this re-implements it by hand today (read the last 2-3 published pieces, eyeball the structure).

**Why not now, the real reason**: the design only has a statistical proxy for structural similarity (paragraph-count buckets, burstiness), and that proxy measures sameness of *shape*, not sameness of *narrative device*. Two pieces can match on every statistic here and use completely different structures (an anecdote vs. a numbered framework vs. a contrarian-claim-then-reveal), or the reverse: same device, different stats. Shipping the statistical version as-is risks a false-confidence green check that doesn't mean what a reader would assume it means, worse than no signal at all, since a passing check invites trust it hasn't earned.

**What would need to be true before building this**: a real answer to both directions of the "same device, different stats" / "same stats, different device" mismatch, not just the statistical proxy. That likely means identifying narrative-device categories as a qualitative signal (closer to `reference/audit.md`'s "Qualitative signals" section, a reasoning step, not a regex) rather than a purely numeric fingerprint. Until that exists, this stays undesigned past the sketch above.

**Secondary cost, also real but not the blocker**: this would be the first place clearfelt reads outside the single target file being scored. Every other command's scope is one file (or one directory scanned independently, file by file). Reading a directory *as context* for scoring a different file is a real behavioral change worth its own design pass, not a one-line addition.

## Feature D: Platform-scoped non-negotiables within one voice profile

**What it would do**: lightweight inheritance for voice profiles. `voice.mode: multi` already supports named profiles (`.clearfelt/voices/<name>.md`) for multiple *writers* sharing a project. This would extend that to multiple *surfaces* one writer publishes to from the same project, e.g. `.clearfelt/voices/x-post.md` with `extends: base` at the top, inheriting everything from a shared base profile and only overriding the fields that genuinely differ (LinkedIn bans markdown headers; X bans exclamation marks and has a hard character ceiling now covered by Feature B's constraints instead). Without inheritance, two platform variants would duplicate the 90% of a voice profile they share (preferred words, sentence rhythm, non-negotiables that apply everywhere).

**Problem it would solve**: one project, one writer, multiple publishing surfaces with genuinely different hard rules. `voice-profile.md` is currently one-per-project (or one-per-named-writer in multi mode); there's no way to say "same person, same core voice, but this specific surface has two extra non-negotiables" without either duplicating the whole profile or forcing every surface to share identical non-negotiables even where that's wrong.

**Why not now**: it's a real gap in the model, but not an active one. Nothing in the shipped rule dictionary today actually flags the kind of platform-specific device this would protect (checked directly: `rules/antipatterns/formatting_tells.md` and `structural_tells.md` have no rule matching emoji headers, contrast-bullet formatting, or similar deliberate devices as of this writing). Building an inheritance system to solve a conflict that doesn't currently occur is exactly the kind of speculative abstraction this project's own design principle argues against. If a real rule ever does start flagging a legitimate cross-surface device, or if `.clearfelt/domain.md`'s single project-wide exemption list stops being enough to cover two surfaces' differing needs, that's the trigger to revisit this, not before.

**What would need to be true before building this**: an actual, observed conflict, not a theoretical one, plus confirmation that `.clearfelt/domain.md`'s exemption list and a project's existing single voice profile genuinely can't express what's needed. Both Feature B's constraint sets (already surface-scoped, by design, via `--constraints <name>`) and a plain second voice profile in `multi` mode are worth ruling out first, since both already exist and might cover the real need without a new inheritance mechanism at all.

## Why these live here instead of as GitHub issues or a TODO comment

Per this project's own `CLAUDE.md`, decisions this consequential normally get an ADR (`docs/decisions/`). Both of these stayed out of that directory deliberately: an ADR documents a decision that was *made*; these are decisions that were explicitly *deferred*, with the conditions for revisiting them written down so a future session doesn't have to reconstruct the reasoning from a Slack thread or a closed PR. If either of these ever does get built, that's when it earns a real ADR of its own.
