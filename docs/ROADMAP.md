# Roadmap

Not a backlog, not a promise. This documents features that were designed and deliberately **not** built, so the reasoning is preserved instead of re-litigated the next time someone asks "should clearfelt-writing do X." If you're considering building one of these, read the "Why not now" section first, it's there to be argued with, not skipped.

Features C and E came out of the same design pass that produced `templates/constraints.example.md` and the personal-calibration work in `scripts/calibrate.mjs` (see `CHANGELOG.md`). That pass evaluated every proposed gap against one test: **can it be described without naming a platform, a person, or a project?** Anything that failed that test either got redesigned into a generic primitive (constraints, calibration) or landed here instead of shipping. Feature F came later, from a separate CPO-lens review of clearfelt-writing's actual reach, but earns its place here on the same standard: a real, named gap, deliberately not built yet, with the reasoning and the reopening conditions written down. Feature G came later still, from a real shadow-drafting session catching one genuine scoring blind spot (a word choice that read odd to a human but scored well), and passed the same "evidence before infrastructure" bar the whole dictionary is built on rather than being sketched from first principles.

## Feature C: Structural-variety check against a corpus

**What it would do**: a generic `--avoid-repeating <dir>` flag on `/clearfelt-writing audit` and `/clearfelt-writing write`. For the most recent N files in the given directory, compute a lightweight structural fingerprint (opening-sentence shape, paragraph-count bucket, burstiness/MATTR proximity, all signals `scripts/lib/score.mjs` already computes, no new statistical machinery) and report similarity as a new, informational report section, alongside readability, not folded into the Human Score.

**Problem it would solve**: nothing today compares a new draft against a writer's own recent output. Every rule in `rules/antipatterns/` and `rules/banned_words/` scores one document in isolation. A writer who publishes serially (a blog, a newsletter, a weekly social post) and wants to avoid "this reads like my last three pieces" currently has no way to check that automatically; every downstream workflow that cares about this re-implements it by hand today (read the last 2-3 published pieces, eyeball the structure).

**Why not now, the real reason**: the design only has a statistical proxy for structural similarity (paragraph-count buckets, burstiness), and that proxy measures sameness of *shape*, not sameness of *narrative device*. Two pieces can match on every statistic here and use completely different structures (an anecdote vs. a numbered framework vs. a contrarian-claim-then-reveal), or the reverse: same device, different stats. Shipping the statistical version as-is risks a false-confidence green check that doesn't mean what a reader would assume it means, worse than no signal at all, since a passing check invites trust it hasn't earned.

**What would need to be true before building this**: a real answer to both directions of the "same device, different stats" / "same stats, different device" mismatch, not just the statistical proxy. That likely means identifying narrative-device categories as a qualitative signal (closer to `reference/audit.md`'s "Qualitative signals" section, a reasoning step, not a regex) rather than a purely numeric fingerprint. Until that exists, this stays undesigned past the sketch above.

**Secondary cost, also real but not the blocker**: this would be the first place clearfelt-writing reads outside the single target file being scored. Every other command's scope is one file (or one directory scanned independently, file by file). Reading a directory *as context* for scoring a different file is a real behavioral change worth its own design pass, not a one-line addition.

## Feature E: Virality/engagement optimization ("clearfelt-writing viral")

**What it would do**: a mode or command that rewrites or drafts a post to maximize its chance of high engagement/reach on a given platform, informed by patterns known to correlate with performance out there (hook formulas, posting patterns, structural devices observed to spread).

**Problem it would solve**: a writer who wants not just human-sounding, voice-consistent text (what `write`/`rewrite` already do) but text shaped toward a specific platform's engagement dynamics.

**Why not now, the real reason**: this fails the same test every other feature here was checked against, worse than Feature C did. Feature C proposed a purely statistical proxy for "does this repeat my own recent structure" and got deferred because a statistical proxy for structural sameness can't distinguish "same shape, different narrative device" from "same device, different shape": a false-confidence signal is worse than none. Virality prediction has no equivalent proxy candidate at all: it isn't a property of the text, computed the same way every time, the way vocabulary diversity or a banned phrase is. It's a correlational guess about audience behavior, timing, and a platform's current algorithm, none of which `scripts/detect.mjs` (or anything content-only) can measure. There is no deterministic score to compute here, only a bet dressed up as one.

It also fails the project's own generality test on a second axis: what spreads on LinkedIn has nothing to do with what spreads on X or in a newsletter, so this is platform-specific by construction, not a generic primitive like calibration or constraints turned out to be.

A third problem, distinct from the first two: this one cuts against what the tool is *for*, not just what it can measure. "Patterns known to work" tends to converge on proven formulas, hook templates, engagement-bait phrasing, the same handful of structural tricks that perform because everyone's using them. That convergence is compositionally close to what `rules/antipatterns/` and `rules/banned_words/` exist to strip out. A viral mode risks becoming a mode for reintroducing the exact homogenized patterns the rest of the tool detects and removes, just ones that happen to convert. That's not a missing feature, that's tension with the project's premise.

**What would need to be true before building this**: a way to express "optimize for engagement" as a property of the text itself, computed deterministically, not a correlational bet, plus a resolution of the tension with the anti-slop premise above (why optimizing for known-to-perform patterns wouldn't just be re-injecting the thing the tool removes). Neither of those has an answer sketched yet, unlike Feature C and D above, which at least have a concrete "what would need to be true." Until one exists, this stays a dead end, not a deferred design.

**Where this actually belongs instead**: a platform-and-writer-specific body of "what's worked for me" (engagement history, competitor/creator research, evidence-backed post-mortems) is real and worth having, it just isn't a generic clearfelt-writing primitive. It belongs in the consuming project, fed into `/clearfelt-writing write`'s existing seed/interview as ordinary context ("match this pattern that's tested well for me"), the same mechanism already used to pick a structure template. See e.g. a project's own analytics/research tooling (creator pattern libraries, post-mortems of what drove performance) as the natural home for that knowledge, with clearfelt-writing staying the voice-consistent, human-sounding drafting layer underneath it.

## Feature F: A non-CLI delivery surface, for non-technical writers

**What it would do**: some way to run clearfelt-writing's scoring and rewriting without a terminal, an agent, or Markdown config authorship, a hosted web form, a browser extension, a lightweight API, that runs `scripts/detect.mjs`'s existing scoring logic (already zero-dependency, already pure functions in `scripts/lib/`) directly.

**Problem it would solve**: today, clearfelt-writing ships as a `git clone`/skills-CLI install, read through an agentic coding tool like Claude Code. That reaches developers who also write. It structurally excludes the population most anxious about "sounding like AI," students, marketers, non-technical writers, who have no terminal, no agent, and no reason to hand-edit a `.clearfelt-writing/voice-profile.md`. "Generic enough for anyone" is currently false for exactly the audience most likely to want this.

**Why not now, the real reason**: this is a different product, not a bigger version of this one. `CLAUDE.md` has a standing hard rule: "Claude Code only, v1, for anything we build... unless that scope decision is revisited explicitly and recorded as a new ADR." A hosted surface reverses that rule, and takes on a trust commitment this repo has never had to make: `scripts/detect.mjs` today runs 100% locally, zero network calls, by construction, the strongest privacy claim it has (see the README's "Runs entirely on your machine"). A hosted form handling someone else's unpublished writing is a real data-handling responsibility, a different security posture, and arguably a different product with clearfelt-writing's scoring engine inside it, not "clearfelt-writing, but on the web." Reversing the CLI-only rule needs to be a deliberate, explicit decision by whoever owns this repo's direction, not a side effect of a roadmap entry.

**What would need to be true before building this**: evidence of real demand from outside the current CLI-fluent, agent-using user base, not assumed from "more reach is generically good." And, separately, an explicit decision to revisit the "Claude Code only, v1" rule in `CLAUDE.md`, recorded as its own ADR before any code gets written, per that rule's own stated exception path.

## Feature G: General word-choice naturalness detection

**What it would do**: a signal that catches an odd, unnatural word choice in general, not just a hand-listed set of known bad phrases. Two designs were scoped, at different cost tiers:

- **N-gram surprisal**: score how statistically unexpected each word is given its immediate neighbors, using conditional-probability or PMI lookups against a reference-corpus bigram/trigram frequency table (COCA-style or Google-Ngram-derived). Catches the general class (odd adjective, wrong preposition, awkward verbing, unusual collocations), not just noun-as-verb.
- **Verb-lemma dictionary check**: a narrower, cheaper design targeted specifically at the noun-forced-into-verb-slot case. Strip common verb inflections from a candidate word (reusing `scripts/lib/rules.mjs`'s existing `inflectionPattern` machinery) and check the stem against a shipped list of recognized verb lemmas (WordNet's ~11,000-entry verb list, public domain). A word that parses as verb-shaped but isn't a real verb lemma is a likely denominal-verb formation.

**Problem it would solve**: `scripts/lib/score.mjs`'s vocabulary-diversity signal (MATTR) measures how often word *types* repeat, not whether a word is the natural, expected one for its context. It has no way to distinguish a rare-but-well-chosen word from a rare-but-odd one, and can actively reward the odd choice, since rarity alone raises the score. Found directly: a clearfelt-writing-drafted shadow post verbed "due diligence" into "diligences it" while independently paraphrasing a source sentence, and that choice measurably raised the document's MATTR score relative to the natural "audits it," the opposite of what a naturalness check should do. See `tests/fixtures/word-naturalness-log.md` for the running record of real cases like this.

**Why not now, the real reason**: both designs need shipped reference data this repo has never taken on for anything else. Every existing statistical signal (MATTR, burstiness, paragraph variety) is computed from the target document alone, zero shipped data. Every existing word/phrase list (`rules/antipatterns/`, `rules/banned_words/`) is small, hand-curated, and reviewable in one glance in a PR, matching `CONTRIBUTING.md`'s whole review model. An n-gram frequency table is tens of megabytes; even the cheaper verb-lemma dictionary is a new class of shipped asset (a large, externally-sourced list nobody hand-reviews line by line) that nothing else in this repo requires. Building either from a single observed case would also repeat a mistake this project has specifically avoided before: `docs/decisions/0011` and `0017` only added or reweighted a statistical signal after measuring it across many real documents, not from one anecdote.

**What would need to be true before building this**: the cheap fix (a new `rules/antipatterns/*.md` bullet per observed case, logged first in `tests/fixtures/word-naturalness-log.md`) needs to actually become the bottleneck, real, repeated cases piling up faster than a hand-written rule can reasonably keep pace with, not a hypothetical ceiling. At that point the verb-lemma dictionary is the more realistic next step of the two (smaller, more targeted, cheaper to source and review than a full n-gram table), and n-gram surprisal stays the "real" general solution to reach for only if the dictionary approach turns out too narrow in practice, not the default first move.

## Why these live here instead of as GitHub issues or a TODO comment

Per this project's own `CLAUDE.md`, decisions this consequential normally get an ADR (`docs/decisions/`). All four stayed out of that directory deliberately: an ADR documents a decision that was *made*; these are decisions that were explicitly *deferred*, with the conditions for revisiting them written down so a future session doesn't have to reconstruct the reasoning from a Slack thread or a closed PR. If any of these ever does get built, that's when it earns a real ADR of its own.
