# ADR 0021: Platform-scoped voice inheritance, driven by setup

**Status:** Implemented
**Date:** 2026-08-19

## Context

ROADMAP's Feature D sketch (`docs/ROADMAP.md`) proposed `extends:` inheritance for `.clearfelt/voices/<name>.md`, so one writer publishing to several surfaces could share a base profile instead of duplicating it per surface, but deferred it: nothing in the shipped rule dictionary flagged a real cross-surface device, so the gap was theoretical.

It stopped being theoretical during a real integration (`executive_assistant`, a personal-brand content project, adopting clearfelt for its LinkedIn drafting). Two concrete conflicts surfaced:

1. `.clearfelt/voice-profile.md`, written under `voice.mode: single`, already contains LinkedIn-only rules (a 👇 CTA convention, alternating between exactly two named structures) sitting in a file the config treats as project-wide, not LinkedIn-specific.
2. The same project's X.com content has its own real, independently-documented hard rules for the same writer: 1-2 hashtags, not 3, an 8-word hook target instead of a 100-character one, no 👇-CTA convention, and self-deprecation encouraged where the LinkedIn voice doc explicitly restricts unpaid earned-edge admissions. A single flat voice profile cannot correctly serve both without either the LinkedIn-only rules leaking into X drafts or someone hand-maintaining two fully duplicated files.

Separately, `voice.mode: multi` and `.clearfelt/voices/<name>.md` already exist (ADR 0007), but are framed entirely around multiple *writers* sharing one project, selected by typing a name into the setup wizard. Nothing in that flow, or in the underlying file format, is platform-aware, and `scripts/lib/config.mjs`'s `loadVoiceProfileOverrides`/`loadVoiceProfileCalibration` read exactly one file with no merge step: hand-authoring an `extends:` line today would do nothing.

A mechanism-only fix (just teaching `config.mjs` to follow `extends:`) would ship a capability nobody discovers without reading source, the same problem `reference/setup.md`'s wizard rule exists to prevent for every other profile field. The feature isn't the merge logic, it's making platform-scoped voices something a user sets up the same way they already set up everything else here: through the picker, not by hand-authoring frontmatter.

## Decision

1. **`extends: <name>` as a one-line directive** at the top of a `.clearfelt/voices/<name>.md` file, naming another file in the same `voices/` directory. One hop only, no chained inheritance (`c extends b extends a` is rejected with a plain error naming the file and the illegal chain), keeping resolution a single lookup, not a graph walk.

2. **Merge policy, per section of `templates/voice-profile.example.md`**, resolved once by `config.mjs`, not left to each caller to reimplement:
   - **List sections** ("Words I want to keep using," "Words to avoid," "Non-negotiables"): union. Base and override both apply; the override file only ever adds, it can't silently drop a base entry. (A writer who genuinely wants to *lift* a base non-negotiable for one platform states that explicitly as its own override entry, e.g. "Unlike the base voice, self-deprecation is fine here," rather than by omission.)
   - **Prose sections** ("Sentence rhythm"): override replaces base outright if the override file sets it; otherwise inherits base's text unchanged.
   - **Personal calibration**: inherits base's four computed fields unless the override file has its own non-`(unset)` calibration block, in which case the override's numbers win outright (all four fields together, never a partial mix). Most platform profiles will never set this section at all, since it's the writer's underlying rhythm, not a platform trait, but a writer whose X voice is genuinely, measurably different from their LinkedIn voice isn't blocked from saying so.

3. **`/clearfelt setup` gains a platform-scoping path.** When a user is setting up multi-voice, ask (through the wizard picker, one question, per `reference/setup.md`'s existing rule) what `voice.mode: multi` is being used for: **Multiple writers sharing this project** (today's existing flow, unchanged) / **Multiple platforms for one writer** (new) / **Both**. Choosing a platform-scoped path:
   - Asks which platforms this project writes for, one at a time, through the picker: **General** as the one concrete, structural option (it's the base role, not a named platform, and always gets created, holding whatever the writer says is true everywhere, even if every other answer is platform-specific), plus the picker's own **Other** free-text slot as the only way to name an actual platform, with a couple of platforms named only as illustrative example text in the question's description ("e.g. LinkedIn, X, a newsletter"), never as their own dedicated buttons. This is deliberate: `LinkedIn` as a hardcoded preset button fails this project's own generality test ("can it be described without naming a platform, a person, or a project?", `docs/ROADMAP.md`) as much as `clearfelt viral` did, just at smaller scale, and it's inconsistent with how every other open-ended question in `reference/setup.md` already works (sentence rhythm offers generic categories like "Short and punchy," never a named product).
   - Collects more than one platform as a loop, not a multi-select over a fixed list (a picker can't multi-select over an open-ended set it doesn't know in advance): ask one platform name at a time via Other, then a plain yes/no follow-up, "add another platform?", until the answer is no. Scales to however many platforms a writer actually has without the wizard needing to know any platform's name ahead of time.
   - Runs the same one-question-at-a-time interview `single` mode already runs (`reference/setup.md` steps 2-6), once for `general.md` with no `extends:` line, then once per named platform, writing `extends: general` automatically and asking only what's platform-specific: "Anything about how you write differs on \<platform\>? A different hook length, a rule that applies here but not generally, something the general voice gets wrong for this platform." Skippable, same as every other setup question; skipping produces a platform file that's just `extends: general` with nothing else, correctly inheriting everything.
   - "Both" runs the writer-name loop from today's flow, then the platform loop per writer, nesting the same one-hop `extends:` model rather than a new one (a per-writer, per-platform combination is `voices/<writer>-<platform>.md`, `extends: <writer>-general`); this is the one part of the decision that stays a sketch, not fully specified, since no real multi-writer-and-multi-platform project has been observed yet, only single-writer-multi-platform. Build it when one is.

4. **`scripts/explain.mjs`** shows the *resolved* profile for a given `--voice <name>`, one line per field, each tagged with its source (`general.md` or `<name>.md`), the same provenance pattern it already uses for `clearfelt.config.md` value sourcing.

## Why

The two-conflict bar Feature D's own deferral set is met, concretely, not hypothetically, by one real project's actual files, not a constructed example. Building the setup path alongside the merge logic, rather than the merge logic alone, matches this project's own established taste: every other profile field is wizard-driven, hand-editing `.clearfelt/*.md` directly is the fallback for power users, not the primary path, and a feature only reachable by hand-authoring `extends:` frontmatter would be the one exception to that.

Union-by-default for list sections, rather than override-replaces, exists because silent narrowing is the more dangerous failure mode here: a platform file that's supposed to add a hook-length rule but accidentally drops a base non-negotiable (say, the em-dash ban) by omission is a much worse outcome than a platform file that's slightly more restrictive than intended. Explicit lift, not implicit drop.

One-hop-only `extends:` is deliberate, not a placeholder for deeper chains later: every real case in hand (LinkedIn extends general, X extends general) is one hop, and a chain-resolution graph is exactly the kind of speculative generality this project's design principle argues against building ahead of a real second-hop case.

## Consequences

- `voice.mode: multi`'s meaning broadens from "multiple writers" to "multiple writers, multiple platforms for one writer, or both," disambiguated by what setup asks, not by new top-level config. Existing multi-voice users with no `extends:` line in any of their files are unaffected: a file with no `extends:` line resolves exactly as it does today, zero forced migration. Verified directly: `tests/explain.test.mjs`'s pre-existing multi-voice tests still pass unchanged.
- Shipped: `scripts/lib/config.mjs` (`resolveVoiceChain`, the one-hop guard, list-union in `loadVoiceProfileOverrides`, inherit-or-override in `loadVoiceProfileCalibration`), `scripts/explain.mjs` (resolved profile with per-field provenance: `extends`, `basePath`, `keptWordsFromBase`/`keptWordsFromOverride`, `personalCalibrationSource`), `reference/setup.md`'s new platform-scoping branch (with the generality fix: General plus Other, looped collection, no hardcoded platform buttons), `templates/voice-profile.example.md`'s `extends:` documentation, and the corresponding instruction in `prompts/write_loop.xml` and `prompts/audit_loop.xml` for the sections `config.mjs` doesn't parse (words to avoid, sentence rhythm, non-negotiables are read directly by the agent as prose, not machine-merged).
- New test coverage: `tests/explain.test.mjs` (one-hop resolution, calibration inherit vs. override-wins, missing-base error, two-hop-chain rejection, no-`extends:`-line unaffected) and `tests/detect.test.mjs` (a base-only kept word still suppresses a hit through a platform override, the real behavioral effect, not just a unit check). `node --test`, `node scripts/eval.mjs`, and `node scripts/lint.mjs` all pass; 100% line coverage maintained on every touched file.
- `executive_assistant`'s existing `.clearfelt/voice-profile.md` (single mode) is the first real migration target: split into `.clearfelt/voices/general.md` (universal rules, the existing 185-post personal calibration) and `.clearfelt/voices/linkedin.md` (`extends: general`, the LinkedIn-only rules already identified: CTA convention, hook shape, structure alternation), switching the project to `voice.mode: multi`. `.clearfelt/voices/x.md` follows later, when X content actually gets drafted through clearfelt, not speculatively now.
