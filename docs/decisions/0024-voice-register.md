# ADR 0024: Voice register, a non-scored tone-match advisory

**Status:** Implemented
**Date:** 2026-08-20

## Context

A real drafting session (`executive_assistant`, the same LinkedIn pilot ADR 0021-0023 came out of) produced a Friday CTA line, "What's the tell that someone's faking it?", that read as more aggressive than the writer intended, next to a same-topic draft that used the gentler "doesn't actually get it." Both phrasings scored identically on the Human Score: the score measures whether text reads AI-written, not whether its tone matches the writer's intent, and those are genuinely different questions.

The instinct that followed was to fold tone into the existing rule dictionary as a new banned-word category, catching "aggressive" words the way `rules/banned_words/puffery_lexicon.md` catches "seamless." That framing doesn't survive contact with how clearfelt is scoped: whether a word reads aggressive is not evidence a document is AI-written or human-written, so scoring it would conflate two different claims inside one number, the same failure mode `docs/decisions/0023` (language-confidence) deliberately avoided by keeping its warning out of the score entirely.

The framing that does hold up: "sound like a human" was never one target. Real humans range from blunt to diplomatic, and clearfelt already models part of a writer's individual voice in `voice-profile.md`'s prose fields (calibrated vocabulary, sentence rhythm, non-negotiables). A tone axis is the missing dimension of that same idea, not a new detector bolted alongside it, and it belongs in the voice profile precedence chain ADR 0021 already built, not in the scored rule dictionary.

## Decision

1. **A new voice-profile field, `register:`**, read from a `## Register` section in `.clearfelt/voice-profile.md` or `.clearfelt/voices/<name>.md`, three values: `neutral` (default), `direct`, `warm`. Resolution precedence matches "Sentence rhythm" in ADR 0021 exactly, since both are prose-style, non-list fields: an override file's own `## Register` wins if set; otherwise it inherits the base file's (`extends:` chain, one hop); otherwise `neutral`.

2. **Two new rule-shaped word lists**, `rules/register/accusatory.md` and `rules/register/hedging.md`, same bullet format as every other rule file (`- word | severity: N | source: key`), but loaded through a separate function, `loadRegisterRules()`, never merged into `loadRules()`'s scored `all` set. `register: warm` activates the accusatory list (words too harsh for a warm voice: fake, fraud, lying, scam...); `register: direct` activates the hedging list (words too soft for a direct voice: maybe, perhaps, i think...); `neutral` activates neither, so a project that never touches this feature never even loads these files' matches into a hit.

3. **Never scored.** A register hit never reaches `computeScore`. It surfaces only as a new `registerCheck: { register, hits }` field in `--mode report`'s payload, present only when `register !== 'neutral'` (an unset or neutral voice sees byte-identical output to before this feature existed, same "only present when it actually fires" convention as ADR 0023's `languageWarning`). Unlike `languageWarning`, `registerCheck` does not appear in `--mode score`'s compact payload: a low language confidence changes whether the score number means anything at all, so `write_loop.xml`/`audit_loop.xml`'s iterative score-only calls need to see it; a register mismatch doesn't affect what the score means, it's a separate, non-blocking note, so it doesn't need to intrude on the terse payload those loops iterate against.

4. **`--register <value>` as a CLI override**, same precedence shape as `--exempt-repetition`: a per-invocation convenience for testing a register without editing a voice file, with the voice profile as the actual place a project states its persistent choice. An unrecognized value (CLI flag or voice-profile field) is a hard error, not a silent fallback to neutral, consistent with how a malformed `extends:` chain already fails loudly rather than guessing.

5. **Tier-clustering is bypassed for register hits** (`findHits(..., { includeSuppressed: true })`). Tier 2/3 suppression in `rules.mjs` exists specifically to keep the *score* honest against a single legitimate word choice; a register hit never touches the score that suppression protects, and applying it anyway silently dropped a real, isolated mismatch during testing (a lone "faking" in a short sentence, the exact real-world case that motivated this ADR, was suppressed because tier 2 requires a second nearby hit). An advisory note has no reason to hide an isolated occurrence.

6. **`source: editorial`, not a `docs/SOURCES.md` key.** README's "every rule cites real research" claim is scoped explicitly to `rules/antipatterns/` and `rules/banned_words/` (`docs/SOURCES.md`'s own opening line). `rules/register/` is a new, separate directory outside that scope on purpose: an accusatory-vs-hedging word list is a curated tone categorization, not a claim about AI-generated text, and dressing it up with a research citation it doesn't have would be worse than plainly labeling it `editorial`, the same honesty bar `unresolved-*` already enforces elsewhere in this project.

## Why not the alternatives considered

**Folding it into the existing banned-word dictionary, scored.** Rejected in the Context section above: conflates "reads AI-written" with "reads tonally mismatched," two different claims, inside one number a reader can't unpack after the fact.

**A project-level `domain.md` field instead of a voice-profile field.** `domain.md` holds project-scoped facts (mode, risk tier, technical jargon exemptions), things true regardless of which voice is speaking. Register is explicitly about "which type of human," a trait of a specific voice, so it belongs where `voice-profile.md`'s other individual-writer traits (vocabulary, rhythm) already live, and it needs to vary per platform the same way `linkedin-short.md` and `linkedin.md` already carry different non-negotiables.

**A continuous "aggression score" instead of three discrete values.** A numeric dial implies a precision this heuristic doesn't have: two curated word lists can say "this word tends to read harsh" or "this word tends to read soft," not "this document is 0.73 aggressive." Three coarse, humanly-legible values match what the underlying signal can actually support, the same reasoning `intensity`'s four named tiers (ADR 0009) used over an arbitrary numeric slider.

## Consequences

- Shipped: `rules/register/accusatory.md`, `rules/register/hedging.md` (new directory), `scripts/lib/rules.mjs` (`loadRegisterRules`), `scripts/lib/config.mjs` (`loadVoiceRegister`, `readRegisterField`, `VALID_REGISTERS`), `scripts/lib/report.mjs` (`registerHits` computation, `registerCheck` payload field), `scripts/detect.mjs` (`--register` flag, validation, wiring into both single-file and directory-scan `runFile` calls).
- A project with no `register:` field anywhere, or `register: neutral`, sees zero behavioral change from before this ADR: no extra rule-file load cost beyond the two small files, no new report field, byte-identical `--mode score` and `--mode report` output. Verified directly: `tests/detect.test.mjs`'s neutral-vs-no-flag test asserts identical scores and an absent `registerCheck` key.
- New test coverage: `tests/rules.test.mjs` (`loadRegisterRules` returns separate, non-overlapping lists; register entries never leak into `loadRules()`'s scored set) and `tests/detect.test.mjs` (warm/direct hit detection, score invariance across all three register values, isolated-hit non-suppression, voice-profile field resolution, `extends:` inherit-vs-override precedence, invalid-value rejection at both the CLI and voice-profile layers, `--mode score` never carrying `registerCheck`). `node --test`, `node scripts/lint.mjs`, and `node scripts/eval.mjs` all pass; 100% line coverage on every touched file.
- `templates/voice-profile.example.md` documents the new `## Register` section; `reference/write.md` and `reference/rewrite.md` note that a fired `registerCheck` should be surfaced to the user during `/clearfelt write`/`rewrite`, the same "disclose, don't silently act on it" pattern ADR 0023's language warning already established.
- This is a new, backward-compatible capability behind an opt-in field and flag, not a change to existing scoring behavior: per the SemVer convention `docs/RELEASE.md` already documents (minor bump = new command/capability/flag), this ships as part of the next minor release, not folded into the already-tagged v0.6.0.
